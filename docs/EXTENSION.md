# 为什么分享扩展思路与可运行参考，而不是原样上传生产扩展？

我们倾向于**分享扩展代码**，但要分清“能参考”和“可以安全照搬”。

生产扩展长期迭代后会带有私人中继地址、旧迁移标记、内部数据格式、历史兼容路径、隐私命名、具体 token 放置方式，以及为当时网页结构临时适配的分支。把它们简单搜索替换后公开，既可能漏泄细节，也会误导读者认为它能在任意环境运行。

这个仓库先分享一个 **clean-room DOM-only** MV3 最小版本，完整包含 `manifest / content / background / extractor / popup`，可以本机运行并验证 `preview → collector → hook ACK`。它刻意不提供读取 ChatGPT 内部会话 API 的生产适配代码，也不包含任何与特定个人、内部 VPS、原文仓库或私有记忆服务绑定的实现。

## 生产版与公开版的区别

| 功能 | 生产概念 | 公开参考 |
| --- | --- | --- |
| Chat 会话识别 | 当前网页 route ID + 更严格的身份检查 | `/c/<id>`，无 ID 则不抓 |
| 消息来源 | 网页可见文本，视场景还可能读取登录态网页内部 API | **仅 DOM，可见节点** |
| 缓存及去重 | 对话 ID、消息 ID、辅助指纹、消费游标 | 按消息 ID 的简单增量，ACK 后记录 |
| 一次性交接 | 生产 collector + ready/consume/fail | 小型本地演示 collector |
| 连续性与记忆 | 私有分层 MCP、长期记忆、档案、短期存储 | 文档 + Hook 模板 + 简单短期存储 |
| iOS 换窗 | 仍不可靠 | **一样不解决** |

这不是在藏一份万能的“真正源码”：原始生产版高度绑定个人环境，公开版主动把不具备泛用价值的复杂度拿掉。

## 将来要公开更完整的生产适配时

1. 以新目录整理源文件，**不要**从带历史的私人 Git 仓库直接公开一个分支。
2. 检查第三方文件是否被复制；如有，按上游相应许可证保留完整版权与许可通知。
3. 替换真实 URL、IP、令牌、身份名称、目录与回滚补丁；不要把 `.env`、Chrome storage 快照或 JSONL 原文随项目打包。
4. 所有默认行为使用 dry-run；添加端点配置与单独授权；严格限制第三方主机权限。
5. 添加回归测试，特别是：两个窗口、错误 route、同文不同 ID、API/DOM 不匹配、ACK 前异常、中止后下一轮恢复。
6. 清楚描述：来自网页内部 API 的采集具有变化风险，且未经官方支持。

开源质量的标准不是代码行数，而是**别人不会因为误读这份 repo，把聊天数据上传到不认识的地方**。
