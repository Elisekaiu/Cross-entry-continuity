# 为什么选择这样的设计？

## 1. 不是所有叫 webhook 的东西都一样

这里需要的是**普通 Chat 自身的每条新消息/回复 → 私人服务器**的可订阅事件。现阶段没有面向普通用户的稳定通用接口。ChatGPT Work 已提供 **针对支持的外部应用事件** 的 Scheduled / webhook 触发任务（例如特定 Gmail、Slack 和 GitHub 活动），但它不是「普通 Chat 消息 webhook」。两种触发方式解决的是不同的问题。

官方说明：
- https://help.openai.com/en/articles/10291617-scheduled-tasks-in-chatgpt
- https://help.openai.com/en/articles/20001275-chatgpt-work-and-codex

## 2. 为什么不把聊天搬进 Work？

主要日常对话发生在 Chat；我们希望 Chat 和另一边的 Agent 同时跑不同任务。Work 能做很多事，但为了跨端连续性而重新安排主要聊天入口，对这个场景不合适。Scheduled / event-triggered tasks 还会引入任务配额、触发条件、使用额度与独立会话语义，不等于免费、无限、实时获取 Chat 原始消息。我们更喜欢保留 Chat 和独立 Agent 两条线程，把轻量的**上下文交接**交给脚本。

## 3. 为什么不每次让模型总结？

每条消息都总结会重复消耗模型调用、延迟、token 和上下文。我们优先用非模型脚本做截取/去重/游标/消息存储。只有目标模型在开始回复时，才接收真正需要的 2–4 条背景或一个 checkpoint。能不注入，就不注入。

## 4. 为什么需要 checkpoint？

扩展不一定在线、网页当前标签不一定正确、网页 DOM 可能变。如果官端自身**已经有调用工具的能力**，在决定/调试工作刚发生而另一入口接不上时，主动写一条「目前在做 X、下一步是 Y」，就能绕过采集失败。它很短，却足够让另一边知道当时的工作进度。

## 5. 为什么失败就放弃？

这是一座私人上下文桥，不是支付系统。偶尔缺失一条聊天比重复注入、混错对话或让 Hook 堵住 Agent 更糟。每个 transition 最多一次自动抓取流程；ready 可以稍后消费，failed 不自动重建，新官方活动产生新 revision。**重要的人工操作仍应显式确认**，不要仅凭这座桥执行高风险操作。

## 6. 为什么对长期人机陪伴与跨端 Agent 也有意义？

长期聊天往往发生在不同产品、设备或线程；短期“刚刚发生什么”与长期“我们此前决定了什么”并非一种信息。跨端连续性可以减少重复解释、保留双线程的独立性，也可以让关系记忆保持克制，不把每条短期碎片永久存储。

我们想保留的是真实而轻盈的连续性：刚刚的近况与长期记忆各有位置，需要时自然接上。
