# 其他没有消息 webhook 的聊天端，如何参考？

本项目讨论的是**跨入口的近期上下文接续**，不是某个品牌的官方同步功能。对普通个人助手、长期陪伴型 Agent、跨设备与双线程创作都可能有价值。

## 先判断哪些能力真实存在

| 能力 | 有就可以做什么 | 没有怎么办 |
| --- | --- | --- |
| 平台官方的消息事件/webhook | 优先直接订阅，少一层网页解析 | 看是否有用户有权访问的网页、导出或历史 API |
| 合规的本人网页/导出读取能力 | 获取“来源明确”的最小消息增量 | 不要偷猜；只用手动 checkpoint |
| 长期开启的浏览器/桌面进程 | 运行扩展或本地采集器 | 改为手动导出/分享，不能承诺即时性 |
| 第二入口的 Hook / 消息前处理 | 在下一条真实消息前按需消费 | 由用户手动调用工具，不要无限轮询 |
| 第二入口的可见对话日志 | 用非模型程序按游标发回短期事件 | 用授权导出或主动 checkpoint 替代 |
| Chat 侧可调用的 MCP/插件 | Bootstrap / continuity_read / checkpoint | 只能复制摘要或手动触发，不能假装自动调用 |

## 推荐的降级路线

1. **最小版**：两个入口共享一个短期存储；用户或模型主动写 checkpoint，另一端按需读取。这已经能避免很多重复叙述。
2. **日志版**：允许时使用本地文件游标导出另一端可见的用户和最终助手消息，不请模型反复总结。
3. **网页采集版**：只有本人合规可访问聊天内容、能验证当前会话身份时，再加入扩展 + 任务/ACK。
4. **官方事件版**：如果另一个平台之后提供稳定合法的消息 webhook，应优先替换不稳定的 DOM/私有 API 层。

## 实测边界

- **已验证的生产设计**：ChatGPT 普通 Chat + iOS Shortcut 转场信号 + 桌面 Mac/Chrome + 私人 Linux VPS + 独立 Agent Hook/日志 + 可调用的记忆工具。
- **仅理论可行**：Windows/Linux Chromium、其他网页 AI 聊天产品、其他消息 App、其他 Agent Runtime。必须单独测试页面语义、登录、平台条款、后台运行和接口限制。
- **不能推论**：iPhone 当前 Chat 窗口被自动识别；网页标签会跟随手机切窗；每次新对话一定会自动 bootstrap。

对于长期人机陪伴，值得保留的是**持续而可追溯的上下文**，不是制造不存在的记忆。短期 continuity 到期会消失；长期记忆应单独征求保存许可并允许更正。
