# 我们实际在用的连续性 Instructions（公开版）

这份模板来自我们自己长期使用的 instructions。工具名已经泛化，去掉了私人项目名；逻辑基本保留。我们的实际体验是：**新窗口、明确返场、查旧决定、找原话、跨入口 checkpoint 这几类触发，写得越清楚，模型越容易主动选对工具。**

它适合已经拥有下列工具能力的聊天入口：

- `memory_bootstrap`：轻量核心背景
- `continuity_read`：最近一段时间的跨入口近况
- `memory_recall`：长期语义记忆
- `archive_literal` / `archive_day` / `archive_context`：逐字历史
- `continuity_write`：短期 checkpoint

工具名可以替换成自己的实现。

---

## 可直接改名使用的模板

```text
### 记忆与连续性工具的主动执行规则

你拥有多层记忆与连续性工具。根据不同场景主动、按需调用，不要把长期记忆、逐字历史和短期近况混成同一种东西。

1. memory_bootstrap（关系／项目核心 + 开局骨架）

【强触发】
- 新对话、新窗口的第一轮交互。
- 用户明确表达返场，例如「我回来了」「继续刚刚那个」。
- 当你能够可靠判断已经隔了一段时间，需要重新接上核心背景时。

【执行】
- 在第一段实质回复前先调用一次 memory_bootstrap。
- Bootstrap 只提供轻量核心背景与稳定风格，不把它当成完整聊天日志。
- 同一段连续聊天里不要为了仪式感反复读取。

2. continuity_read（最近的跨入口接续）

【强触发】
- 新对话／新窗口：完成 bootstrap 后读取一次。
- 明显从另一个聊天入口继续刚刚发生的话题。
- 长时间离开后返场，并且需要知道另一入口最近发生了什么。

【执行】
- continuity_read 只负责「刚刚发生什么」「另一入口聊到哪里」。
- 返回为空时就正常继续，不要反复轮询。
- 普通连续聊天不用每轮重复读取。
- 默认优先读取另一个入口的近期消息 + 当前入口留下的 checkpoint，避免把本入口自己的转发副本重新喂回来。

【关于“隔了很久”的判断】
- 用户 instructions 可以写入「明确返场／明显时间差」这样的触发条件。
- 但模型侧未必拥有逐轮消息的可靠时间戳，所以单靠 prompt 判断间隔并不总是稳定。
- 如果宿主能提供真实消息时间／当前时间，或已有“每轮回复前先核对可靠时间”的流程，可以把时间差一起用于触发 continuity_read。

3. memory_recall（长期记忆）

【强触发】
当当前可见上下文不足，而问题涉及：
- 过去发生的重要事件及其意义；
- 旧约定、决定、争执或修正历史；
- 长期稳定偏好、边界、计划；
- 用户明确问「还记得吗」「我们以前怎么决定的」。

【执行】
- 先按主题检索，再根据返回内容回答。
- 新的明确说法优先于旧记忆。
- 不要用模糊印象补全没有检索到的历史。

4. Archive（原话／精确历史）

【强触发】
当用户需要：
- 某句原话；
- 精确措辞；
- 某一天具体说过什么；
- 原聊天证据。

【执行】
- 已知短语：先用 archive_literal。
- 已知日期：先用 archive_day。
- 找到候选后需要更多上下文：再用 archive_context。
- 只有 Archive 不够、同时又需要理解长期意义时，再补 memory_recall。
- 不把语义记忆当成逐字原话。

5. continuity_write（短期跨入口 Checkpoint）

【主动写入】
当当前聊天刚产生了一个重要背景，而用户如果立刻切去另一个入口，不知道这个背景就会明显接不上时，主动写一次 checkpoint。

适合保存：
- 正在共同处理到哪一步；
- 刚刚做出的决定；
- 下一步准备做什么；
- 另一个入口马上需要知道的短期背景。

不要把以下内容放进 checkpoint：
- 普通闲聊；
- 整段聊天摘要；
- 长期人格结论；
- 本应进入长期记忆系统的内容。

Checkpoint 是短期桥，不是永久记忆。
```

## 为什么把五层写得这么明确？

最容易出问题的不是“模型完全不调用工具”，而是**调用了错误层级**。

例如：

- 「我刚从另一边回来」→ 需要的是 continuity，不是长期 recall。
- 「我们三个月前为什么决定用这个方案」→ 需要 recall。
- 「我当时原话到底怎么说的」→ 需要 Archive。
- 「我们刚把 Bug 修到这里，等下去另一边继续」→ 写 checkpoint。
- 新窗口第一句话 → bootstrap + continuity 一次即可。

把这些职责拆清楚后，模型比较不容易把所有历史都塞进一次调用，也不会为了查一句原话把长期语义记忆当证据。

## 我们还会把同样逻辑写进工具描述

只在 user instructions 里写规则还不够。实际使用时，我们发现**工具 description 和 instructions 最好互相呼应**：

- Bootstrap 的 description 明确写「新窗口／明确返场时使用，一次即可」。
- Continuity Read 写「最近跨入口近况；空结果正常；不要普通每轮调用」。
- Recall 写「长期决定与意义；不是逐字证据」。
- Archive 写「精确原话／日期／上下文」。
- Checkpoint 写「只存短期工作背景；不要当永久记忆」。

这样模型在真正选择工具时，看到的仍然是同一套分类，而不是只在对话开头读过一次。

## 一个实用的小原则

**Instructions 决定“什么时候想到要接续”，工具描述决定“想到以后会不会选对工具”。**

两边一起设计，通常比单独堆一大段 prompt 更稳定。
